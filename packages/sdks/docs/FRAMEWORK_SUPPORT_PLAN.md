# Plan: minimum supported framework versions for Builder SDKs

## Outcome

Give pre-sales, support, and developers one reliable answer to: *Is this customer's framework version supported by the SDK they use?* The answer must distinguish versions that a package manager permits from versions Builder actively tests and supports. The current branch documents mostly `peerDependencies` lower bounds; those are useful installation facts, but they do not establish a support policy. For example, the Gen 1 React SDK permits React 16.8 and Widgets permits Next.js 12.3.5, while the Next.js RSC SDK has a different Next.js requirement.

Done means each published framework-facing SDK has either an owner-approved, tested support floor or an explicit statement that no active minimum is verified; customers can find that status in a central matrix and the package README, and changes to it have a review and verification path. Do not present an unverified version as supported merely because it satisfies a peer range.

## Scope and decisions

- Cover Gen 1 `@builder.io/react`, `@builder.io/angular`, `@builder.io/gatsby`, and `@builder.io/widgets`; and the Gen 2 React, React Native, Vue, Angular, Svelte, Solid, Qwik, and Next.js RSC packages under `packages/sdks/output/`. Treat Widgets' Next.js requirement as conditional on using Next.js.
- Document Next.js **by integration**: standard Gen 1/Gen 2 React SDKs and the RSC-specific Next.js SDK are not interchangeable. Do not infer a Next.js support floor for the standard React SDKs from the RSC package's `next` peer dependency. Keep the unqualified “all versions of Next.js” claim out of `packages/sdks/output/nextjs/README.md`; describe the standard React integrations separately until their support floors are verified.
- Mark the Android sample in `packages/android/README.md` as unpublished/development-only, not as a customer-supported SDK. Framework-agnostic packages are outside this matrix.
- Define **peer-compatible** as accepted by `peerDependencies`; **supported** as a version family with an explicit team commitment and a passing representative integration test; and **unverified/legacy** as installable but outside that commitment. A floor alone does not promise that every later major version works: state supported major ranges or exceptions where needed.
- Determine the numerical active minimum for each SDK during implementation, not before starting the work. SDK owners and support approve the resulting cutoffs and treatment of upstream-EOL releases. Do not infer support from manifests or silently raise peer dependencies: changing an installation range is a separate potentially breaking release decision.

## Implementation

1. **Derive an active minimum or document the gap for every SDK.** For each package/integration above, record its published SDK version, framework and companion-framework peer ranges (for example React + React DOM, or React Native + React), current CI coverage, upstream lifecycle status, and known limitations. Start with `packages/*/package.json`, `packages/sdks/output/*/package.json`, `.github/workflows/ci.yml`, and package READMEs. Choose a candidate minimum that is upstream-maintained and satisfies the package's peer range; test the actual SDK integration at that version with its required companion frameworks. If the candidate fails, record why and test the next viable version; if no candidate can be tested, leave the row **support policy pending** rather than guessing. Record the selected version, supported major range, test evidence, and any EOL exception for SDK-maintainer and support sign-off, especially for Gen 1 React/Next.js and Widgets. Do not call a version actively supported before both verification and approval.
2. **Publish one customer-facing source of truth.** Expand the existing matrix in `packages/sdks/README.md` to clearly separate Gen 1, Gen 2, and integration-specific Next.js guidance (or move the cross-generation matrix to an agreed shared location and link to it). Each row should name the npm package, applicable framework(s), actively supported minimum/range, status or limitations, and a link to the exact manifest peer range. Keep package READMEs as short summaries linking to that matrix; add the missing local note in `packages/sdks/output/angular/README.md`. Ensure the same guidance reaches the public developer docs used by sales and support, with an explicit owner for that publishing step.
3. **Correct misleading prose.** Update `packages/react/README.md`, `packages/widgets/README.md`, `packages/sdks/output/react/README.md`, and `packages/sdks/output/nextjs/README.md` so React 16 and Next.js 12 are classified according to the approved policy, not implicitly endorsed just because installation is allowed. In `packages/sdks/output/react-native/README.md` and `packages/sdks/output/svelte/README.md`, avoid “or later” promises that conflict with their `^18.0.0` React and `^4.1.2` Svelte peer ranges. State the exact package/major-version context for historical SDK releases rather than treating the latest SDK policy as retroactive.
4. **Maintain the claim.** Add a framework-support review item to `packages/sdks/PUBLISHING.md` and the relevant Gen 1 release process: a peer-dependency change, new framework major, test-matrix change, or upstream end-of-support event triggers owner review of the matrix, local READMEs, and public docs. Keep a small automated check that every supported minimum satisfies its package's peer range and that every in-scope SDK is represented; couple it with representative minimum-version CI coverage in `.github/workflows/ci.yml` or clearly mark exceptions as unverified. Do not make the prose table an unmaintained substitute for tests.

## Policy decisions and approvals

- **Approved by the owner:** upstream-EOL versions are not actively supported by default, even when peer-compatible. For React, use a tested modern major rather than counting legacy security backports as full active support. Document coverage gaps instead of expanding SDK compatibility in this pass.
- **Still required per row:** select and test the exact minimum framework/companion-framework combination, then obtain owner approval of that numerical cutoff or explicitly state that no active minimum is currently verified.
